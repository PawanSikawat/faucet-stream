## BigQuery (`crates/sink/bigquery/`)

**`src/merge.rs`** — new pure, unit-tested SQL generation (`// Scoped cleanup (issue #478)` section):
- `build_cleanup_delete(...)` emits a **single** `DELETE FROM t T WHERE &lt;scope&gt; AND NOT EXISTS (SELECT 1 FROM UNNEST(JSON_QUERY_ARRAY(@keys)) AS k WHERE &lt;key&gt;)`. Exactly **two** bound params — `@scope` (one JSON object) and `@keys` (a JSON array) — both extracted with the same typed `column_expr` the write path uses, so an INT64 key compares as INT64. A single DML statement is atomic in BigQuery, which is what gives all-or-nothing.

## Spanner (`crates/sink/spanner/`)

Read-then-delete inside **one** `read_write_transaction`. Refactored `build_delete_mutation` into `encode_key_in_pk_order` + `delete_mutation_from_kinds` so the cleanup shares the encoding. New pure helpers: `scope_cast_expr`, `scope_param_text`, `build_scope_select_sql`, `kind_fingerprint`/`tuple_fingerprint`, `stale_key_rows`, `check_cleanup_cell_budget`. 14 new unit tests + 5 emulator tests.

Two things worth flagging:

1. **Scope params are bound as STRING and cast in SQL** (`CAST(@scope_0 AS INT64)`, `FROM_BASE64(@scope_0)` for BYTES, bare `@scope_0` for STRING). The client derives a param's Spanner type from the *Rust* type it's handed, but a cleanup scope carries `serde_json::Value`s whose destination type is only known at runtime from `INFORMATION_SCHEMA`. Casting keeps one binding path for all column types — the same trick as BigQuery's `JSON_VALUE(@scope, …)`. `JSON`/`ARRAY`/`STRUCT` scope columns are refused (no equality semantics). Values still route through `encode_to_kind` so type mismatches fail locally, and both sides of the comparison are encoded through the destination type, so a written key of `"7"` and a live INT64 of `7` match.

2. **Documented limitation — the cell budget cannot be chunked.** `chunk_by_cells` is unusable here: the read and the delete must commit together, and a transaction commits exactly once, so chunking would mean several commits — a partial cleanup where every chunk after the first decides from an already-stale snapshot. Instead `check_cleanup_cell_budget` refuses up front (deleting nothing) when the stale set would exceed `CELL_BUDGET`, with a message naming the count and suggesting a narrower `complete_for`. That threshold (60k cells) sits well above the per-parent scopes the feature targets and above core's own `max_keys` reachability. The rationale is spelled out in a comment on that function.
