## MongoDB composite-key approach
BSON has no tuple `$nin`, so the "not written" clause is key-width dependent and documented as such:
- **Single-column key** → `{ &lt;key&gt;: { "$nin": [v, …] } }` (index-servable).
- **Composite key** → `{ "$nor": [ {a: …, b: …}, … ] }` — "matches none of the written tuples". Rejected alternatives are documented inline: a derived `_id` only works when the key *is* `_id` (this sink treats `key` as an arbitrary match filter, and it would mismatch pre-existing documents), and `$expr` forces a collection scan with no index use.

Everything is wrapped in `{"$and": [...]}` with one clause per predicate rather than sibling fields, because a scope field may also be a key field (`contact_id` scope + `["contact_id","assoc_id"]` key) — as siblings the duplicate map entry would drop the scope predicate and widen the delete to the whole collection. There's a regression test for exactly that. Empty `seen` drops the negation clause (also avoiding an invalid empty `$nor`), leaving the scope predicate alone so the whole scope is deleted.

## Elasticsearch atomicity caveat (documented on `cleanup_scope_impl`)
ES has no transactions: `_delete_by_query` snapshots, then deletes in batches, so the scope passes through partially-cleaned states that concurrent searches observe, and a mid-flight failure leaves some stale docs deleted and others not. Two things make that safe rather than merely tolerable, and both are stated in the comment: (1) the query excludes every written `_id`, so no partial outcome can remove a document this run wrote — only stale ones, in some order; (2) a partial outcome is never reported as success — `deleted_from_delete_by_query` converts any `failures`, `version_conflicts`, or `timed_out` into an error naming how many documents *were* removed, and the next run re-derives the same scope and finishes (deletion is idempotent). Version conflicts leave the document in place (`conflicts=abort` default) rather than deleting on a stale snapshot.

Two extra correctness guards on both sinks: a `check_key_alignment` refusal if a written-key tuple isn't keyed by the sink's `key` in order (for ES the order is load-bearing — `key_to_doc_id` is order-sensitive), and an explicit refusal of an empty scope at the sink boundary (defence in depth behind `CleanupPolicy::new`).

Bounds are hard stops, not chunking, in both sinks — splitting the written-key set across queries would make each query delete the keys the others excluded. Errors name the ceiling, the server limit behind it, and say "Nothing was deleted".
