## Dialect decisions worth flagging

1. **SQLite quoting is backticks**, unlike the rest of that sink (which uses `faucet_core::util::quote_ident` → double quotes). SQLite's double-quoted-string misfeature turns an unresolvable `"col"` into a *string literal* — in a `DELETE` predicate that silently deletes the wrong rows instead of erroring. I added a local `quote_ident_sqlite` for the cleanup path only and did not re-quote existing code (out of scope, and it would churn existing test expectations).
2. **Temp table qualification.** SQLite: always `temp.faucet_cleanup_keys` so the defensive `DROP` can never hit a real table of that name. MySQL: `CREATE/DROP TEMPORARY TABLE` — session-scoped, shadows a base table only for that session, and (crucially) these are the two DDL statements MySQL does *not* implicitly commit, so the delete stays all-or-nothing inside the transaction.
3. **No `DELETE … AS alias`** in either dialect — MySQL only allows it from 8.0.16, and the correlated reference works identically via the table name. Verified empirically for SQLite by the integration tests.
4. **MySQL temp columns carry `CHARACTER SET`/`COLLATE`** copied from the destination column; without it, a table whose key column overrides the schema default raises "Illegal mix of collations" on the join. Type specs are re-emitted from the catalog behind a shape allowlist (fallback `LONGTEXT` for MySQL, typeless column for SQLite).
5. Both drop the temp table defensively before creating (pooled connection reuse) and again before commit.

Empty `seen` is explicitly not short-circuited in either sink — `NOT EXISTS` against an empty key table deletes the whole scope, and there are dedicated tests for it in both crates.
